# Customer conversation UI: prepared, inactive

This dependent PR adds an isolated customer page for the [conversation contract](CUSTOMER-CONVERSATIONS.md). It does not change the existing repair form, navigation, live endpoint, Google prefill, analytics, dashboard sync or staging workflows. The shipping configuration is `{enabled:false, endpoint:''}`. No production portal or customer communication is activated.

## Customer behavior

`customer-conversation.html` asks one missing structured question at a time. **Only name and callback number are required**, matching the existing ordinary short form's contact minimum. A first name is fine. The page explains that these help Tony find the request and know who to call back; it requires no login. A short problem, vehicle, starts/drivable status and general vehicle location are optional. Every optional question has explicit Not sure and I'll add this later choices. Once contact details are present, Skip optional details and review defers only missing optional fields, preserving supplied answers. The ordinary short repair form remains prominently available inside the enabled page as well as the inactive fallback.

Version 2 uses typed `{state:'provided',answer:...}`, `{state:'unknown'}` and `{state:'later'}` choices. No answer property or invented customer text accompanies an unknown/later choice. Missing optional fields mean later. Only provided choices become canonical guide/customer pairs on the server; a name-and-phone-only inquiry saves four such message rows. These rows describe structured form choices saved when Send succeeds, not fabricated pre-send chat timestamps. The browser's raw intake omits unprovided optional keys; `repair.fieldStates` preserves their typed states separately. Existing lead normalization is unchanged; nullable vehicle fields would need a separate versioned private contract patch.

A resumed tab draft skips answered choices. Back and per-answer Edit support corrections without asking completed questions again. The review step explicitly says the draft has not been sent. Explicit Send submits one reviewed version 2 intake and its provided clarification answers to the existing Cloud Intake conversation API. Version 1 editable drafts migrate to typed choices; already-pending version 1 request bodies stay byte-for-byte equivalent on retry. There are no appointment or SMS-permission controls in this slice; the shop's existing booking and consent flows remain separate. Omitting an optional detail does not classify a request as spam.

On a durable server receipt, the page shows saved messages and **Details in the initial request**, with unknown/later states labeled as states at intake. Customers can supply optional repair details later in messages. Those messages do not silently change the initial snapshot, its states or any staff notes. A pending create or reply is saved in tab session storage before its network request. Lost acknowledgments retain the original operation ID and body through reload. Receipt reconciliation can prove a previous send saved without resending it. A matching receipt followed by a failed message refresh displays **saved, refresh unavailable**, with a usable Refresh control.

Opening the same private link preserves pending recovery. Opening a different conversation keeps the first resource's pending operation separately and never sends it to the second resource. A same-ID link with a different token fails closed without overwriting the original pending state. Per-resource session records can contain unsent customer text and scoped bearer access; they remain sensitive and are removed by the browser when its tab session ends. The page does not claim permanent account history or automatic cross-device identity.

Explicit Copy private return link puts the one-conversation capability in a URL fragment. The page removes that fragment before application fetches. It loads no third-party assets, standard website script or analytics; requests omit cookies and referrers, prohibit redirects and request no cache storage. Unavailable, expired or revoked access locks the view and reply controls. Messages and repair fields are rendered with text nodes. API reads drain up to ten 100-message pages, matching the backend's 1,000-message cap, and reply acknowledgment never replaces the older read cursor or skips an intervening shop reply.

## Safe local preview

The ordinary static staging build includes only this page's inactive fallback. It strips the two conversation script tags and does not copy the conversation transport or protocol modules. The staging guard still blocks contact actions and network traffic. Use the separate memory-only preview below to exercise the optional guide; merging this source does not enable staging conversations.

From this checkout, run `node tools/preview-customer-conversations.mjs --port=18947`, then open `http://127.0.0.1:18947/customer-conversation.html`. It binds loopback only, serves only this page's allowlisted files, visibly labels itself synthetic, uses memory-only mock data and sends no notifications or external requests. Stopping that owned process discards its synthetic records. It is a UI preview, not a deployable backend or integration proof.
